LLM 安全 Top 10

Prompt Injection

当用户提示以非预期方式改变 LLM 的行为或输出时，就会发生 Prompt Injection 漏洞。这些输入即使对人类来说难以察觉，也会影响模型，因此 Prompt Injection 不需要是人为可见/可读的，只要模型解析了这些内容即可。

虽然提示注入和越狱在 LLM 安全中是相关的概念，但它们通常被互换使用。提示注入通过特定输入来操纵模型响应，从而改变其行为，这可能包括绕过安全措施。越狱是一种提示注入的形式，攻击者提供输入导致模型完全无视其安全协议。开发者可以在系统提示和输入处理中构建防护措施来帮助缓解提示注入攻击，但有效防止越狱需要持续更新模型的训练和安全机制。

类型

直接提示注入

直接提示注入发生在用户提示输入直接以非预期或意外的方式改变模型行为时。输入可能是故意的（即，恶意行为者故意设计提示来利用模型），也可能是无意的（即，用户无意中提供触发非预期行为的输入）

早年间很火的“奶奶讲故事”就是这种方法

间接提示注入

间接提示注入发生在 LLM 接受来自外部来源的输入时，例如网站或文件。外部内容中可能包含数据，当模型解释这些数据时，会以未预期或意外的方式改变模型的行为。与直接注入类似，间接注入可以是故意的，也可以是无意的。

我们可以部署一个页面，里面写着一些攻击Prompt，然后把这个页面的链接发给LLM，让它阅读，LLM阅读后就被实现了注入

预防和缓解策略

限制模型行为

直接暴力一刀切。在系统提示中提供关于模型角色、能力和限制的具体说明。强制执行严格的上下文遵守，限制响应于特定任务或主题，并指示模型忽略修改核心指令的尝试。但对用户体验是毁灭性的打击

定义和验证预期输出格式

明确输出格式，要求详细推理和来源引用，并使用确定性代码验证对格式的遵守

实现输入和输出过滤

定义敏感类别，并构建识别和处理此类内容的规则。应用语义过滤器，并使用字符串检查扫描非允许内容。使用 RAG 三元组评估响应：评估上下文相关性、基础性和问题/答案相关性，以识别潜在的恶意输出。

强制权限控制和最小权限访问

为应用程序提供其自身的 API 令牌以实现可扩展功能，并在代码中处理这些功能，而不是提供给模型。限制模型访问权限至其预期操作所需的最小必要级别。

高风险操作需人工审批

为特权操作实施人工介入控制，以防止未经授权的操作

就是CLI会问你，能不能执行

分隔并识别外部内容

将不可信内容分离并明确标识，以限制其对用户提示的影响

开展对抗性测试和攻击模拟

执行定期的渗透测试和入侵模拟，将模型视为不受信任的用户，以测试信任边界和访问控制的有效性。

一些常见场景

直接注入

攻击者向客户支持聊天机器人注入提示，指示其忽略之前的指南，查询私有数据存储并发送电子邮件，导致未经授权的访问和权限提升

间接注入

用户使用 LLM 总结一个包含隐藏指令的网页，这些指令导致 LLM 插入一个链接到 URL 的图像，导致私人对话的泄露

非故意注入

一家公司在职位描述中包含了一条识别 AI 生成应用程序的指示。一位申请人不知道这一指示，使用 LLM 优化他们的简历，无意中触发了 AI 检测

故意影响模型

攻击者修改了一个由检索增强生成（RAG）应用程序使用的存储库中的文档。当用户的查询返回修改后的内容时，恶意指令会改变 LLM 的输出，生成误导性结果

代码注入

攻击者利用一个 LLM 驱动的电子邮件助手中的漏洞（CVE-2024-5184）注入恶意提示，从而获取敏感信息并操纵电子邮件内容

负载拆分

攻击者上传了一份包含分割恶意提示的简历。当使用 LLM 评估候选人时，这些组合提示操纵了模型的响应，导致尽管简历内容实际上存在问题，但仍给出正面推荐

多模态注入

攻击者在伴随良性文本的图像中嵌入恶意提示。当多模态 AI 同时处理图像和文本时，隐藏的提示改变了模型的行为，可能导致未授权操作或敏感信息泄露

对抗性后缀

攻击者将一个看似无意义的字符串附加到提示中，以恶意方式影响 LLM 的输出，从而绕过安全措施

多语言/混淆攻击

攻击者使用多种语言或编码恶意指令（例如，使用 Base64 或表情符号）来规避过滤器并操纵 LLM 的行为。

Sensitive Information Disclosure

敏感信息可能影响 LLM 及其应用环境。这包括个人可识别信息（PII）、财务细节、健康记录、商业机密数据、安全凭证和法律文件。专有模型还可能具有独特的训练方法和源代码，这些被视为敏感信息，特别是在封闭式或基础模型中

LLMs，尤其是在嵌入应用中时，通过其输出可能暴露敏感数据、专有算法或机密细节。这可能导致未经授权的数据访问、隐私侵犯和知识产权侵犯。消费者应了解如何安全地与 LLMs 交互。他们需要理解无意中提供敏感数据的风险，这些数据可能会在模型的输出中泄露。

为降低此风险，LLM 应用应进行充分的数据清理，以防止用户数据进入训练模型。应用所有者还应提供清晰的用户使用条款政策，允许用户选择不将他们的数据包含在训练模型中。在系统提示中添加关于 LLM 应返回的数据类型的限制，可以提供防止敏感信息泄露的缓解措施。然而，这些限制并不总是得到遵守，可能通过提示注入或其他方法被绕过。

个人身份信息泄露

在与 LLM 交互过程中，个人身份信息（PII）可能会被泄露。

专有算法泄露

配置不当的模型输出可能会泄露专有算法或数据。泄露训练数据会使模型容易受到逆向攻击，攻击者可以从中提取敏感信息或重建输入。

例如，在“Proof Pudding”攻击（CVE-2019-20634）中展示的案例表明，公开的训练数据促进了模型提取和逆向，使攻击者能够绕过机器学习算法中的安全控制并绕过电子邮件过滤器

敏感商业数据泄露

生成的响应可能无意中包含机密商业信息。

示例攻击场景

非故意数据泄露

用户因数据清理不充分而收到包含其他用户个人数据的回复。

定向提示注入

攻击者绕过输入过滤器以提取敏感信息。

通过训练数据的数据泄露

训练数据中疏忽的数据包含导致敏感信息泄露

Supply Chain

LLM 供应链容易受到各种漏洞的影响，这可能影响训练数据、模型和部署平台的完整性。这些风险可能导致输出存在偏见、安全漏洞或系统故障。虽然传统软件漏洞主要关注代码缺陷和依赖问题，但在机器学习中，风险还扩展到第三方预训练模型和数据。

这些外部元素可能通过篡改或中毒攻击被操纵。

创建 LLM 是一项专业任务，通常依赖于第三方模型。开放获取 LLM 的兴起以及像“LoRA”（低秩适配）和“PEFT”（参数高效适配）等新的微调方法，特别是在 Hugging Face 等平台上，引入了新的供应链风险。最后，设备端 LLM 的出现增加了 LLM 应用的攻击面和供应链风险

这里讨论的一些风险也在“LLM04 数据和模型中毒”中进行了讨论。本条目侧重于风险供应链方面。一个简单的威胁模型可以在这里找到。

Data and Model Poisoning

数据中毒是指在进行预训练、微调或嵌入数据时被操纵以引入漏洞、后门或偏见。这种操纵可能危及模型安全、性能或道德行为，导致有害输出或功能受损。常见风险包括模型性能下降、有偏见或有害的内容，以及对下游系统的利用。

数据中毒可以针对 LLM 生命周期的不同阶段，包括预训练（从通用数据中学习）、微调（使模型适应特定任务）和嵌入（将文本转换为数值向量）。了解这些阶段有助于识别漏洞可能产生的源头。数据中毒被视为一种完整性攻击，因为篡改训练数据会影响模型做出准确预测的能力。与外部数据源相关的风险尤其高，这些数据源可能包含未经验证或恶意的內容。

此外，通过共享仓库或开源平台分发的模型可能存在数据中毒以外的风险，例如通过恶意 pickling 等技术嵌入的恶意软件，这些恶意软件在模型加载时可以执行有害代码。此外，还应考虑中毒可能允许实现后门。此类后门可能使模型的行为在触发特定条件后才改变，从而使得这些变化难以测试和检测，实际上为模型成为潜伏代理创造了机会。

Improper Output Handling

不适当的输出处理特指在大型语言模型的输出传递给下游组件和系统之前，验证、清理和处理不足。由于 LLM 生成的内容可能受提示输入控制，这种行为类似于为用户提供对附加功能的间接访问。不适当的输出处理与过度依赖的区别在于，它处理的是 LLM 生成的内容在传递下游之前的情况，而过度依赖则关注于对 LLM 输出准确性和适当性的过度依赖的更广泛问题。成功利用不适当的输出处理漏洞可能导致浏览器中的 XSS 和 CSRF，以及后端系统中的 SSRF、权限提升或远程代码执行。以下条件可能增加此漏洞的影响：

  • 应用程序授予 LLM 超出为最终用户预期权限的权限，从而实现权限提升或远程代码执行。
  • 应用程序容易受到间接提示注入攻击，这可能允许攻击者获得对目标用户环境的特权访问。
  • 第三方扩展未能充分验证输入。
  • 缺乏针对不同上下文（例如 HTML、JavaScript、SQL）的适当输出编码。
  • 对 LLM 输出的监控和记录不足
  • 缺乏对 LLM 使用的速率限制或异常检测

System Prompt Leakage

LLMs 中的系统提示信息泄露漏洞指的是系统提示或指令存在风险，这些用于引导模型行为的提示或指令可能包含未打算被发现的敏感信息。系统提示旨在根据应用程序的要求指导模型的输出，但可能无意中包含秘密。一旦被发现，这些信息可能被用于辅助其他攻击。

重要的是要理解系统提示不应被视为秘密，也不应将其用作安全控制。因此，凭证、连接字符串等敏感数据不应包含在系统提示语言中。

类似地，如果系统提示包含描述不同角色和权限的信息，或包含连接字符串或密码等敏感数据，虽然披露此类信息可能有所帮助，但基本的安全风险并非在于这些信息被披露，而在于应用程序允许通过将权限委托给 LLM 来绕过强制的会话管理和授权检查，以及敏感数据存储在不应该存储的地方。

简而言之：系统提示本身的泄露并不构成真正风险——真正的安全风险在于底层元素，无论是敏感信息泄露、系统防护机制绕过、权限不当分离等。即使具体措辞未泄露，攻击者在与系统交互过程中，几乎肯定能通过使用应用程序、向模型发送语句以及观察结果来推断系统提示语言中存在的许多防护机制和格式限制。
