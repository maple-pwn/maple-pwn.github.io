# AI 与网络攻防：用 CLI 把大模型组织成可执行的 Agent 工作流

> 使用边界：全文案例统一放在 CTF、课程实验、靶场与授权测试环境中展开。


## 逻辑链概览

很多同学第一次把大模型带进网络攻防场景时，最先得到的是一种错位感。聊天窗口里，它擅长解释概念、整理思路、补代码片段；真正进入题目目录、容器环境、抓包文件、日志样本和调试器之后，工作重心立刻转向连续执行。题目说明散在 `README`、源码、附件和网页提示里，分析动作分布在 `curl`、`grep`、`python`、反汇编器、调试器和浏览器流量导出之间，前一轮刚找到的线索，下一轮很容易在上下文压缩时失去形状，做题过程中积累下来的方法也常常停在个人脑中。整场分享想处理的正是这一层工程距离。

分享会沿着一条连续的逻辑链推进。先讲 CLI，是因为命令行界面（Command-Line Interface，CLI）把文件、命令、环境、日志和产物放在同一个操作表面上，网络攻防里最关键的动作几乎都能在这里接住。随后进入 Agent，因为只要任务跨过单轮问答，系统就必须具备规划、执行、观察和状态延续。再往下，function calling 把“调用什么工具、传什么参数”从自由文本收束成结构化请求；工具一多，MCP（Model Context Protocol）把接入关系整理成统一协议；重复任务积累起来，skills 把经验封装成可复用工作流；任务进入长周期后，harness 负责运行约束、轨迹记录、结果校验和复现实验；知识来源继续扩展时，RAG（Retrieval-Augmented Generation）再把最相关的材料送回当前窗口。最后再回到 Web 题、逆向题和日志研判题，让前面每一个部件都落进同一条求解链路里。


```

flowchart LR
    U[授权实验任务] --> CLI[CLI 工作台]
    CLI --> A[Agent 主循环]
    A --> FC[function calling]
    A --> S[skills]
    A --> H[harness]
    A --> R[RAG]
    FC --> M[MCP 接入层]
    M --> T[Shell 文件系统 代码库 知识库]
    H --> L[轨迹 约束 判分 导出]
    R --> K[题解 协议 手册 历史经验]

```


## 第 0 节：问题背景与分享目标

网络攻防工作流有一个很鲜明的特点：信息密度高，动作粒度细，环境状态又总在变化。做一题 Web 靶场时，题目描述、源码目录、依赖版本、容器编排、HTTP 响应和日志都在说话；分析一份 ELF 样本时，文件头、保护机制、导入表、字符串、反编译结果和调试现场会一层层叠上来；处理课程作业或授权测试时，范围边界、输出格式、证据留存和复现实验同样进入流程。于是整个工作流常常出现五个现实痛点：**信息来源分散，工具链复杂，环境切换频繁，上下文容易断裂，经验沉淀速度跟不上任务复杂度增长**。

CLI 与 Agent 的组合之所以值得单独拿出来讲，原因就在这里。CLI 负责把真实环境暴露出来，Agent 负责把模型、工具、状态和观察结果组织成闭环。只讲大模型，很容易停在“会聊天”；只讲脚本自动化，很多任务里的判断、回看与路线调整又会缺位。把两者接起来，才会出现一种更贴近真实工程的原型：模型持续读取环境状态，调工具拿证据，按约束推进任务，把中间产物落盘，再沿着下一轮执行继续推进。对于已经有基础编程能力、具备基础网络安全知识、接触过大模型产品但工程经验仍在建立中的同学，这条路线的门槛可控，收益也很直接。

这一讲的目标同样很明确。文章会把重点放在“亲手搭出一个 CLI Agent 原型”上，用它辅助处理攻防题目求解与安全研究中的真实子任务。等到分享结束，听众至少应当能回答五个问题：模型在工程里到底输出什么；Agent 主循环怎样形成闭环；function calling、MCP、skills、harness、RAG 各自位于哪一层；CLI 为什么比网页聊天界面更适合这类任务；一个最小系统从哪里起步，走到什么程度就已经能解决一批题目。


## 第 1 节：前置知识

先把最基础的一层摆稳。大模型在底层做的事情，可以理解为根据当前可见信息继续生成下一个 token 序列。进入工程系统之后，这个输出序列经常被约束成更稳定的形状，例如普通文本答复、结构化 JSON、工具调用请求、错误说明和最终结论。于是工程系统真正关心的焦点，已经从“模型会说什么”转到了“模型当前给出的输出，怎样进入外部执行链条”。

为了把这个关系说清楚，可以先做一个符号约定。记模型为 $M$，第 $t$ 轮可见上下文为 $C_t$，工具描述集合为 $T$，外部环境快照为 $E_t$，模型输出为 $y_t$。在工程实现里，当前轮次的求值过程可以写成

$$
y_t = M(C_t, T, E_t)
$$

这里的 $C_t$ 包含系统提示词、用户输入、历史工具结果和已经压缩过的状态摘要；$T$ 表示当前可调用工具的名称、参数模式描述与权限边界；$E_t$ 则对应真实外部世界的某个切片，例如文件树、网络响应、数据库状态、容器现场或调试器读数。这个写法的意义在于，它直接把 prompt、上下文、工具与外部状态放进同一个画面里。大模型从来都处在一个由信息和约束共同构成的工作空间里。

接着看单轮问答与多步执行的差异。单轮问答处理的是一次性的解释与回答，问题进入、答案输出，这一轮就结束了。多步执行任务的结构完全不同。它需要先决定下一步动作，再进入工具调用，等待真实环境返回结果，随后再根据观察结果调整后续动作。只要任务里出现“先读附件，再跑脚本，再看输出，再修正判断”这样的链条，系统就已经离开了单轮问答，进入了闭环执行。

这也是“会聊天”与“会做题、会操作环境、会调用工具”之间的工程距离。聊天模型擅长在已有上下文里生成语言；题目求解与安全研究则要求它在变化中的环境里连续工作。环境状态会变，命令有副作用，文件会被修改，网络请求会返回新信息，长任务会跨越多个上下文窗口，历史还需要被压缩和回收。只要少掉其中任意一层，系统的手感就会从“执行中”重新滑回“讨论中”。

从这一节往后，文章会默认大家已经接受一个前提：把大模型放进工程系统之后，真正重要的对象是任务闭环，单次回答的语言光泽会退到次要位置。这个前提一旦站稳，Agent 的定义就很自然地会浮出来。


## 第 2 节：从聊天模型进入 Agent

工程上最先卡住的地方，通常出现在“下一步由谁决定”。用户给出一道题，模型可以解释这道题；一旦要求它真正推进解题流程，系统就需要持续做出选择：先读哪个文件，先跑哪个工具，遇到输出噪声时怎样收束，线索断掉以后怎样回退。Agent 这个词在这里的价值，正是把这些动作放回同一个执行系统里来理解。

把 Agent 理解成围绕任务闭环组织模型、工具、状态与观察结果的执行系统，会更贴近工程现场。这个定义里有五个核心部件。第一是规划（plan），用来形成当前轮次的动作意图；第二是执行（act），把动作意图落到工具或环境操作上；第三是观察（observe），把工具结果、命令输出和环境变化送回系统；第四是记忆（memory），用于保存跨轮仍然有价值的事实、证据和中间产物；第五是终止条件，用来判断当前任务是否已经达到可交付状态。

这里有一个很重要的 insight。很多网络攻防任务天然就长成多步循环，因为证据本身具有层次。Web 题常见的路径是“读说明 → 启服务 → 枚举路由 → 观察请求响应 → 发现认证或模板线索 → 回查源码 → 再构造请求”；逆向题常见的路径是“看文件类型 → 查保护机制 → 扫字符串与导入符号 → 找关键函数 → 下断点 → 观察寄存器或内存 → 修正假设”；日志研判题常见的路径是“筛时间窗口 → 聚类来源 → 回看失败认证 → 关联进程与网络活动 → 形成时间线”。这些任务的难点始终来自“上一轮的观察怎样改变下一轮动作”，所以 Agent 必须具备持续回看与调整的能力。

记忆层同样值得单独说清楚。很多同学听到 memory 时，会先想到“让模型记住聊天历史”。这个理解只覆盖了很薄的一层。工程里的记忆通常分成三类：短时记忆保存当前会话里仍然要继续使用的事实摘要，中期记忆保存当前任务周期内的 artifact 与状态文件，长期记忆则更适合放在知识库、题解库、检索索引和结构化数据库里。Agent 调用 memory 的过程，可以理解为在不同时间尺度上重新分配上下文容量。

顺着这条链往前走，下一个问题会自然出现：既然 Agent 需要反复读文件、跑脚本、看网络输出、写 artifact，那么哪一种操作表面最适合承载这些动作？这时 CLI 的位置就清晰了。


## 第 3 节：为什么 CLI 是 Agent 的天然舞台

当任务进入真实环境，Agent 最需要的能力是把动作、证据和产物接成一条连续链。CLI 天生适合承载这件事，因为文件系统、脚本、编译器、调试器、网络工具、日志处理程序、容器环境和题目附件原本就聚集在这里。模型只要进入命令行工作台，就能在一个稳定表面上看到目录、启动命令、日志文件、响应输出与结果产物。

CLI 适合 Agent 操作真实环境，首先来自它对“状态”的可见性。当前目录是什么，哪些文件存在，哪个容器在运行，哪条命令产出了什么输出，日志写进了哪里，这些信息都能用命令直接表达。Web UI 很适合阅读资料和交互式展示，IDE 很适合代码浏览、编辑和重构，CLI 更擅长把输入、动作、输出、副作用与 artifact 一次性串进同一条执行链。网络攻防里那些常见动作，例如读取题目附件、运行本地脚本、发起 HTTP 请求、检查 ELF 保护、抓取字段摘要、导出证据，都与命令行天然贴合。

CLI 的第二个价值来自可复现性。命令、参数、工作目录、环境变量、输入文件和输出文件一旦被记录下来，任务轨迹就能被复放。你可以把一轮实验写成 shell 历史、一份 `run.sh`、一个 `Makefile` 目标、一段 Docker Compose 启动流程，甚至一份 harness 日志。对于安全研究和题目求解，这种可复现性十分关键，因为一次看似顺畅的推理，只有在轨迹可复放、结果可重现时，才真正具备工程价值。

举几个具体例子，这一点会更直观。处理一份 Web 题附件时，Agent 可以先扫目录、读说明、跑启动命令，再把产物送回模型做下一步决策：

在这些例子里，模型真正依赖的关键能力有三项。第一项是把输出收束成对下一步有用的摘要，例如从 `tree` 结果里提炼项目结构，从 `curl` 响应里提炼状态码、头部与异常字段，从 `checksec` 结果里提炼保护信息。第二项是把一轮执行的产物继续送回模型，让它依据新观察做下一步决策。第三项是把关键 artifact 落盘，形成可读、可查、可复放的工作痕迹。CLI 在这三项上都非常强，因为它天然擅长把数据流与控制流摆在明处。

只要这一点站稳，下一层摩擦也会很快出现：模型如何稳定地表达“去调用某个外部工具并传入正确参数”。这就是 function calling 的位置。


## 第 4 节：function calling 讲透

工程系统在引入 function calling 之前，最常见的卡点是自由文本的松散性。模型完全可以写出“建议你读取 `README.md` 再执行 `docker compose up -d`”，问题在于这句话很难直接驱动外部执行器。工具名称、参数边界、路径格式、可选字段、默认值、错误形状，全都悬在自然语言里，系统一旦进入复杂工具链，稳定性就会迅速下降。

function calling 的核心工作，就是给模型一条结构化调用通道。开发者先用模式描述（schema）定义工具名称、参数结构、字段类型、必填约束与额外属性规则；模型在当前轮次里输出“调用意图 + 参数”；外部执行器读取这份结构化请求，完成真实执行，再把结果回填给模型。这里的角色分工非常明确：模型负责决定调用什么，执行器负责决定怎样执行，工具结果再作为新观察回流到下一轮推理。

```

此时模型才开始整合结果，生成“服务已启动，监听地址为 `127.0.0.1:8080`，下一步建议用 `curl` 访问首页并检查响应头”的回答。整个过程中，分析与执行被稳定地接在了一起。

再往深一层看，function calling 真正解决的是五个工程问题。第一，schema 让参数边界显式化，模型输出更容易被验证；第二，执行器把“语言决定”与“真实副作用”分开，权限与审计边界变得清楚；第三，工具结果进入统一回填通道，后续推理有了稳定输入；第四，工具本身可以被替换或升级，模型侧接口保持相对稳定；第五，错误恢复可以被收束成明确流程。

错误恢复尤其值得细讲。参数缺失时，执行器通常会先做 schema 校验，再把缺失字段包装成结构化错误回填，让模型补齐参数。参数格式错误时，执行器会返回字段级报错，例如路径超出工作目录、整数超出范围、命令不在允许列表。工具超时时，执行器一般会附带超时标记、已收集输出和建议收缩策略，例如缩短命令、减少输出行数、改用摘要脚本。工具输出过长时，常见做法是截断、摘要或导出 artifact，再把摘要与 artifact 路径回传给模型。重试策略也很有讲究：同一种错误重复出现两到三轮后，系统更适合要求模型换路线，持续撞同一堵墙的收益已经很低。

安全边界同样属于这一层。function calling 自身负责表达结构化调用意图，直接执行真实动作的权限始终掌握在外部执行器手里。也正因为如此，工作目录限制、命令白名单、只读与可写区分、网络范围、人工确认点和日志审计都可以被清楚地挂在执行器上。网络攻防场景里的关键价值就在这里：模型负责分析与决策，执行器负责把决策落到受控环境中。

很多人初次接触时，容易把 function calling 理解成“模型自己会去调工具”。更准确的看法是：模型生成的是调用意图，真实执行发生在系统外层。这一点理解透了，下一层问题就会自然冒出来。工具数量一旦增多，单独维护函数描述很快会变得零散，于是系统需要一层统一的接入协议来管理“有哪些能力可以用，怎样发现它们，怎样以统一方式调用它们”。这就是 MCP 的位置。


## 第 5 节：MCP 讲透

当系统里只有两三个工具时，开发者手写 schema 还很轻松。题目环境一旦扩展到 shell、文件系统、知识库、代码仓库、网页抓取、本地脚本和远端数据源，每一种能力都自己设计一套接法，维护成本会迅速抬高。Agent 工程在这里遇到的核心摩擦，是接入关系碎片化。

MCP 把这件事整理成了协议层。它的基本角色可以分成三类。host 持有用户会话、模型与上层应用逻辑；client 负责与某个 MCP server 建立协议连接、发现能力并转发调用；server 则对外暴露 tools、resources 与 prompts。放在 CLI Agent 里看，host 往往就是本地代理程序或终端工作台，client 是嵌在 host 里的协议适配层，server 则可以连接文件系统、shell、知识库、代码仓库、数据库或题目环境。

这个角色划分之所以重要，是因为它把“模型怎样看见工具”与“工具怎样实现”分到了两层。对模型来说，看到的是统一的能力目录；对后端开发者来说，维护的是若干遵守同一协议的 server。于是原本高度耦合的接线方式，被压缩成了“host 连接多个 server，client 负责协议往返”的结构。

下面这个时序图可以把交互关系讲得更直观一些：


```

sequenceDiagram
    participant H as Host
    participant C as MCP Client
    participant S as MCP Server
    H->>C: 请求发现能力
    C->>S: initialize / list_tools / list_resources
    S-->>C: tools resources prompts
    H->>C: call_tool(read_file, {"path":"README.md"})
    C->>S: JSON-RPC 请求
    S-->>C: 工具结果
    C-->>H: 结构化观察结果

```

对于 Agent 工程来说，MCP 的价值集中在四点。第一，它把工具、资源与提示模板放进统一接口，host 端的接入复杂度会显著下降。第二，它让能力发现变成显式过程，模型可以先看到“系统里现在有哪些可用能力”，再决定要用哪一个。第三，它让本地能力与外部数据源拥有同样的暴露方式，文件系统和知识库因此可以进入同一张能力地图。第四，它为权限、认证、审计与可观测性留下了标准化插口。

在网络攻防工作流里，MCP 特别适合承载五类能力。接入 shell 时，它可以把命令执行放进受控工具集合；接入文件系统时，题目附件、源码目录、日志与导出产物都有了统一读取入口；接入知识库时，题解、协议手册、版本笔记与工具文档可以被按需检索；接入代码仓库时，`git` 历史、文件内容、差异信息和 issue 讨论都能进入上下文；接入题目环境时，本地容器、实验站点、靶场 API 和辅助服务也都能收束到统一协议里。

一个常见误解值得顺手澄清。把 MCP 看成工具协议层，会更准确；把它直接缩成“插件系统”，视野会变窄。插件更多描述分发形式，MCP 讨论的是 host、client、server 之间怎样用统一方式交换能力目录与调用结果。这种标准化带来的工程收益，体现在接入复用与能力治理上。

接入层站稳以后，系统还会遇到另一种摩擦：很多任务具有稳定起手套路，模型每次都从零组织流程，效率仍然偏低。经验沉淀在这里开始变得重要，于是 skills 进入舞台。


## 第 6 节：skills 讲透

只要一个任务跨越多轮规划、执行与回看，经验就会自然积累。Web 题初始侦察经常先看目录结构、启动服务、枚举路由、检查中间件、抓首页响应；ELF 样本初步分析经常先看文件类型、查保护机制、扫字符串、扫导入表、找关键函数；日志研判经常先定时间窗、筛关键字段、按实体聚类、回查上下游行为。若每次都从空白 prompt 开始，系统就会一轮轮重复组织同一类动作。

skills 的工程意义，就在于把这类可复用流程沉淀为工作单元。一个 skill 通常对应一类稳定任务，它会告诉 Agent 在什么条件下触发、进入后按什么顺序推进、优先读取哪些参考资料、优先调用哪些脚本、最终输出哪些 artifact。模型仍然保留现场判断能力，重复性很高的步骤则被收束成可复用结构。

按当前主流 CLI Agent 生态的习惯，一个 skill 的最小结构可以写成这样：


```

web-initial-recon/
├── SKILL.md
├── references/
│   ├── common-auth-chain.md
│   └── flask-routing-checklist.md
├── scripts/
│   ├── route_map.py
│   └── response_digest.py
└── assets/
    └── recon-report-template.md

```

`SKILL.md` 是入口文件，它需要承担五项职责。第一，写清触发条件，例如“当目录中出现 Web 项目结构、容器编排文件或实验说明时触发”。第二，写清任务边界，例如“只做初始侦察与证据整理，深入利用阶段交给后续 skill 或人工确认”。第三，写清执行步骤，例如先读说明、再启动服务、再枚举目录、再抓响应、再生成首轮报告。第四，写清输入输出约定，例如输入目录、基础 URL、运行约束，输出 `recon-report.md` 与若干 artifact。第五，写清常见失败点，例如服务启动延迟、动态路由遗漏、重定向链遮蔽真实入口、登录前置逻辑影响页面可见性。

`references/` 更适合承接按需读取的说明性材料，例如框架路由规则、常见认证链、模板引擎注入条件、协议字段解释和历史经验笔记。`scripts/` 适合承接确定性强、重复编写成本高的代码，例如目录枚举、路由提取、响应摘要、日志切片和结果清洗。`assets/` 适合放模板、样例产物或最终报告骨架，例如一份标准化侦察报告模板、一张固定的图示底板或一个可复用的 HTML 输出框架。这样的目录结构有一个直接好处：SKILL.md 保持轻量，具体材料按需加载，脚本则可以直接执行。

拿一个与网络攻防直接相关的 skill 例子来看，这个结构会更清楚。下面是一份“Web 题目初始侦察” skill 的关键片段：


```

显式调用与隐式匹配在工程上也有分工。显式调用适合课堂演示、批处理与标准流程明确的场景，使用者可以直接说“先跑 `web-initial-recon`”；隐式匹配适合日常协作，系统根据技能描述和当前任务上下文自动判断是否触发。前者强调控制感，后者强调流畅度。两种方式都很有价值，关键在于任务阶段与团队习惯。

另一个常见误解也值得一并澄清。把 skill 理解成一份长 prompt，仍然少看了三层内容：目录结构、外部资源与可执行脚本。真正有工程价值的 skill，核心在“可复用工作流 + 可加载资料 + 可运行脚本”的组合。这样一来，经验才会从一次性提示词成长为长期资产。

当技能层逐渐丰富以后，系统通常会走到下一个门槛：任务已经能跑，下一步想要的是可测、可比、可复现。此时 harness 的必要性就会全面显出来。


## 第 7 节：harness 讲透

在这次分享里，我们给 harness 一个严格定义：harness 是围绕某一类任务建立的执行与评测壳层，它负责题目输入、环境准备、工具暴露、运行约束、轨迹记录、结果判分与复现实验。这个定义有意把“运行”和“评测”放在一起，因为很多看似跑通的演示，一旦进入重复实验、多人协作或模型对比，立刻会暴露出缺少壳层组织的问题。

harness 是 Agent 从“能跑”走向“可测、可比、可复现”的关键一层，原因可以顺着任务生命周期来看。题目从哪里进入，附件如何准备，服务怎样启动，允许哪些工具，步数和时间上限是多少，哪些路径可写，轨迹存在哪里，成功条件如何判定，最终怎样导出结果，这些问题若散在零碎脚本里，系统就很难形成稳定实验面。harness 把这些边界收束到一个统一壳层里，结果才具备对比价值。

一个面向题目求解或安全实验的 harness，至少要包含六个部分。第一部分是输入层，负责题目描述、附件、初始 URL、提示文件和可选标签。第二部分是环境层，负责工作目录、容器启动、依赖准备和本地服务映射。第三部分是工具层，负责暴露哪些 shell 命令、哪些 MCP server、哪些自定义函数以及各自权限边界。第四部分是约束层，负责最大执行步数、总时长、网络范围、文件写入范围与人工确认点。第五部分是轨迹层，负责记录每一轮思考摘要、工具调用、输出摘要、artifact 路径与关键状态。第六部分是评测层，负责定义成功判定条件、证据要求、结果导出格式与复现指令。

输入、环境、工具权限、时间限制、轨迹采集和结果校验之间，是一组相互勾连的关系。输入层决定任务起点，环境层保证每一轮实验都在同样的现场起步，工具层限定 Agent 能做什么，约束层控制成本与风险，轨迹层让全过程可追查，评测层再把“完成任务”变成可机器判定或可人工审核的条件。只要少掉其中一层，系统就很难稳稳站在实验与研究的地面上。

harness 与简单脚本、benchmark、评测平台之间也有清楚边界。简单脚本通常只承接某个动作，例如启动服务或抓取路由；benchmark 更强调跨模型、跨方法的统一任务集合与评价标准；评测平台会继续扩展到任务分发、排队运行、结果看板和团队协作。harness 位于中间，它先把单类任务的执行与评测壳层搭起来，后面无论接 benchmark 还是接平台，都会容易很多。

运行壳层稳下来以后，知识补给又会成为下一层瓶颈。题解、协议、工具文档、版本笔记和历史 writeup 继续堆积，仅靠当前窗口很难承载，于是 RAG 需要进入体系。


## 第 8 节：RAG 讲透

安全知识天然分散在各类材料里。writeup 记录了题型经验，协议规范定义了字段语义，源码暴露了真实实现，论文给出方法论，API 手册说明工具行为，日志样本呈现现场痕迹。只要任务稍微复杂一些，模型就会同时需要版本知识、框架知识、题型知识和工具知识。把所有材料一次性塞进上下文，信息密度会迅速失衡，相关片段反而更难被当前轮次抓住。

RAG 的完整链条，正是为了解决这一类问题。先把知识切分成合适粒度的片段，再建立索引，随后根据当前问题做检索，拿到候选片段后进行重排，最后将少量最相关片段拼接进上下文，并连同来源信息一起返回。这个流程里，每一步都在解决不同类型的摩擦：切分控制信息粒度，索引负责建立可搜索空间，检索负责召回候选，重排负责提升相关性，上下文拼接负责把片段送进当前窗口，引用返回负责让证据链可追查，时效性控制负责让系统优先使用与当前版本、当前年份、当前环境更贴近的材料。

如果用一个更形式化的写法来描述混合检索，可以先做符号约定。设

查询为 $q$，候选片段集合为 $D=\{d_1,d_2,\dots,d_n\}$。稠密检索得分记为 $s_{\text{dense}}(d_i,q)$，关键词检索得分记为 $s_{\text{sparse}}(d_i,q)$，重排模型得分记为 $s_{\text{rerank}}(d_i,q)$。

一个常见的综合评分形式可以写成
$$
S(d\_i, q) = \alpha s\_{\text{dense}}(d\_i,q) + \beta s\_{\text{sparse}}(d\_i,q) + \gamma s\_{\text{rerank}}(d\_i,q)
$$

其中 $\alpha,\beta,\gamma \ge 0$，并由实验环境和任务类型决定。这个式子的含义很实用。语义检索擅长抓“意思相近”的片段，关键词检索擅长抓版本号、函数名、错误码和协议字段，重排阶段再把真正贴近当前任务的片段顶到前面。网络攻防里经常会同时需要这三类能力，因为很多线索兼具语义相似性与精确字符串特征。

RAG 更适合补充哪类知识，也需要说清楚。具有明显时效性、版本依赖性、外部来源性或体量较大的知识，非常适合进入 RAG，例如某个框架的认证链条文档、某个 glibc 版本的利用差异笔记、工具使用手册、课程题库历史题解和协议说明。流程稳定、动作固定、重复出现的经验，更适合写成 skill。需要真实与外部系统交互的能力，更适合作为工具或 MCP server 暴露出来。这样分层以后，知识与动作的边界会非常清晰。

拿一个贴近安全场景的例子来看。假设本地知识库里保存了历届题解、glibc 利用笔记、常见 Web 漏洞利用条件和工具手册。当前 Agent 正在分析一道授权实验环境中的 Web 题，它已经通过目录侦察发现项目使用 Jinja2 模板，日志里又出现了一段异常的渲染输入。此时系统发起检索，查询词包含“Jinja2 模板注入 条件”“沙箱绕过 常见入口”“当前版本 过滤逻辑”。RAG 召回后，重排模块把最贴近当前框架版本与现象描述的片段排到前面，再把三到五段材料连同来源文件一起送回上下文。模型随即就能把历史知识与当前证据对齐，决定下一轮验证动作。

时效性控制在这一层也非常关键。知识库里的材料若跨越多年，系统最好给每个片段加上日期、版本、来源、题型和工具标签。例如 `framework=flask`、`jinja2_version=3.x`、`glibc=2.31`、`source=writeup`、`year=2025`。检索与过滤阶段利用这些元数据，系统才能优先召回当前任务真正相关的材料。这样一来，RAG 提供的是“当前轮次需要的知识补给”，简单堆料很难产生同等效果。

另一个常见误解也很值得澄清。把 RAG 理解成外挂知识库，仍然少掉了召回、排序、引用和时效控制四层关键结构。真正的 RAG 系统是一条受约束的检索链，它要回答的核心问题是：当前步骤最需要哪几段材料，它们来自哪里，它们凭什么排在前面。

到了这里，Agent、function calling、MCP、skills、harness 与 RAG 都已经各自站稳。下一节要做的，就是把这些部件真正串起来。


## 第 9 节：把这些部件真正串起来

现在可以把整条链路重新看一遍。Agent 是任务总控，它持续决定下一步动作；function calling 是模型发起结构化调用的机制，它把调用意图变成可验证参数；MCP 是工具与数据源的标准化接入层，它把 shell、文件系统、知识库和题目环境整理成统一能力目录；skills 是可复用的任务模板与经验封装，它告诉 Agent 某类任务的稳定起手方式；harness 是运行与评测壳层，它负责范围、日志、约束和判分；RAG 是知识补给系统，它把当前最相关的外部材料送回当前窗口；CLI 则是这一切落地执行的操作表面。

把这几个部件放进一条完整工作流里，场景可以设在一套合法授权的 Web 实验环境。用户先给出一道题的说明、附件压缩包和基础 URL。harness 创建工作目录、解压附件、启动容器、写入初始配置，并给本轮任务设定最大步数、可用命令与日志路径。Agent 进入第一轮时，先读取 `problem.md`、`README.md` 和目录树，确定任务处在“初始侦察”阶段。skill 匹配模块发现当前环境符合 `web-initial-recon` 的触发条件，于是把对应流程说明和所需脚本引入当前上下文。

随后，模型通过 function calling 发起两类调用。第一类是受控命令，例如列目录、读配置、访问首页、抓响应头；第二类是结构化分析工具，例如 `route_map.py`、`response_digest.py` 或 `kb_search`。这些调用在 host 侧进入执行器，执行器再通过 MCP client 与文件系统 server、知识库 server 或 shell server 通信。每一步结果都被包装成结构化观察结果，写入 Agent 状态与 harness 轨迹日志。

当系统在源码或响应里发现新的框架线索时，RAG 模块接手知识补给。它根据当前关键词、框架版本、异常现象和历史步骤，在本地知识库中召回相关片段，把经过重排的材料与引用路径一并送回上下文。Agent 在下一轮利用这些材料更新计划，例如把“继续看首页源码”改成“检查模板渲染入口与过滤逻辑”。若验证成功，新的证据再被落盘为 artifact；若验证结果与假设相反，Agent 就沿着观察结果修正路线。

这条链一旦顺起来，题目求解过程会很像一个受控实验。用户给的是任务目标，Agent 负责不断生成局部计划，function calling 把计划落成结构化动作，MCP 提供统一能力入口，skills 贡献稳定套路，RAG 供应局部知识，harness 保证整个过程可运行、可记录、可比较，CLI 则把所有操作变成可复放的命令与产物。最终交付的内容会扩展成一整套证据与过程：命令日志、关键响应、路由摘要、源码线索、引用资料与最终结论。

为了让这条链更容易在分享现场讲清楚，可以把它压缩成一个九步工作流：

1. 用户提交题目说明、附件与目标边界。
2. harness 创建实验目录、准备环境、登记约束。
3. Agent 读取题目说明和目录树，确定当前阶段。
4. skills 提供首轮工作流与推荐脚本。
5. function calling 把模型意图转成结构化工具调用。
6. MCP 把 shell、文件系统、知识库与本地服务接入同一能力目录。
7. RAG 在需要背景知识时召回最相关片段与引用。
8. harness 记录轨迹、收束 artifact、校验成功条件。
9. Agent 输出答案、证据和可复放结果。

很多抽象名词一旦进入这九步，层次关系就会立刻清楚。它们并排站在系统里，彼此各有职责，前后又自然衔接。到这里，整场分享的主体逻辑已经闭合，下一步只剩下“怎样讲、怎样演示、怎样让听众回去后真的能动手”。


## 第 10 节：面向分享现场的演示方案

一小时分享要讲清楚这套体系，节奏设计非常关键。前半段负责把概念和层次摆稳，后半段负责把它们重新汇回一个端到端案例。现场展示的命令行只放在真正有信息增益的位置，图示与伪代码则用来压缩抽象概念的理解成本。

| 环节 | 建议时长 | 适合的呈现方式 | 讲解重点 |
| --- | --- | --- | --- |
| 开场与问题背景 | 5 分钟 | 口头叙述 + 一张总览图 | 为什么网络攻防工作流需要 CLI Agent |
| 前置知识 | 6 分钟 | 白板或投影片公式 | 模型输出、上下文、工具、外部状态的关系 |
| Agent 基础 | 8 分钟 | 伪代码 + 流程图 | 规划、执行、观察、记忆怎样闭环 |
| CLI 位置 | 5 分钟 | 现场终端演示 | 目录、命令、输出、artifact 如何进入同一链路 |
| function calling | 8 分钟 | JSON schema + 一次工具调用过程 | 调用意图、参数、执行器与回填 |
| MCP | 7 分钟 | 配置片段 + 时序图 | host、client、server 与统一接入层 |
| skills | 5 分钟 | 目录树 + `SKILL.md` 片段 | 经验怎样沉淀为可复用工作流 |
| harness | 5 分钟 | YAML 草图 | 约束、轨迹、判分、导出 |
| RAG | 5 分钟 | 检索公式 + 小型知识库例子 | 切分、召回、重排、引用、时效 |
| 端到端案例 | 4 分钟 | 一条九步工作流 | 把所有部件汇回一题 |
| 收束与提问 | 2 分钟 | 口头收束 | 听众带走什么、回去先做什么 |

现场展示命令行时，最适合选三处。第一处放在 CLI 一节，直接展示 `tree`、`sed`、`curl` 这类简单命令，让听众看到“真实环境进入模型链条”的入口。第二处放在 function calling 一节，展示用户问题、工具 schema、工具调用请求与执行结果回填，让抽象机制立刻落地。第三处放在端到端案例，一次性展示题目目录、skill 触发、MCP 工具发现和 artifact 导出，让所有名词重新连回一个工作流。

画图说明最适合放在两处。第一处是开场后的整体架构图，它承担的是“给所有概念安排位置”；第二处是 MCP 时序图或 RAG 检索流，它负责说明系统内部通信与信息筛选方式。伪代码更适合放在 Agent 主循环和 harness 草图部分，因为这两层涉及控制流，代码形态天然比长段描述更容易讲清。

微型安全题案例建议选一题结构清楚、依赖较少、动作链明显的实验题，例如一个本地 Web 靶场或一份小型 ELF 样本。这样一来，现场既能展示文件读取、命令执行和知识检索，又能把系统复杂度控制在一小时分享可承载的范围内。


## 第 11 节：工程经验与落地建议

如果听众分享结束后准备立刻动手，最适合先搭的是一个最小系统：一个模型调用入口，一个 `read_file` 工具，一个 `run_command` 工具，一份简单状态文件，一条 10 到 20 步的主循环，再加一个 artifact 目录。只要这个系统已经能读取题目说明、扫目录、跑几条只读命令、把输出写成简短报告，它就已经开始具备解决题目的能力。很多课程实验和基础 CTF 题，走到这一步便能处理掉第一轮侦察与信息整理。

MCP 适合在工具来源开始多样化时引入。只要文件系统、shell、知识库和代码仓库同时进入系统，统一接入层的收益就会迅速显现。prompt 升级成 skill 的时机，则来自任务重复率：某类任务的起手流程已经稳定，且同一套路在多题里反复出现时，写成 skill 的性价比就很高。RAG 更适合在知识规模开始超过当前上下文容量、版本差异开始影响判断时引入。harness 的优先级则与实验严肃程度相关，一旦你打算重复跑多题、比较多种模型、长期积累轨迹或将结果交给团队复核，harness 就应当尽快补上。

安全研究场景里，最常见的工程摩擦主要集中在五个方面。第一是上下文失真，早期关键线索在长任务里被压缩过度；处理思路是将“已确认事实、待验证假设、关键 artifact 路径”单独写入状态文件。第二是工具噪声，命令输出长度与相关性常常失衡；处理思路是优先让脚本返回摘要、关键字段与 artifact 路径。第三是命令副作用，环境一轮轮运行后会发生漂移；处理思路是把可写目录收束到固定区域，把服务启动、清理和重放流程写进 harness。第四是环境漂移，依赖版本和本地服务状态变化会影响复现实验；处理思路是显式记录镜像、依赖和启动命令。第五是结果可复现性下降，系统给出答案后难以回头检查；处理思路是让每一步关键决策都附带证据来源与执行痕迹。

这里再穿插一组常见误解澄清。把 Agent 直接理解成 prompt 拼接，视野里会缺少状态、工具、观察与终止条件；把 MCP 压成插件概念，协议层的统一发现与能力治理就会消失；把 RAG 缩成外挂知识库，检索链路与引用机制就会失焦；把 harness 理解成测试脚本，运行约束、轨迹记录、结果导出与复现实验这几层也会随之失去位置。很多工程分歧，根源都来自层次边界模糊。

最后给出一条最小可行原型路线图，方便听众分享结束后直接动手：

| 阶段 | 目标 | 交付物 |
| --- | --- | --- |
| 第 1 周 | 跑通最小 Agent 主循环 | `read_file`、`run_command`、状态文件、artifact 目录 |
| 第 2 周 | 把稳定套路写成 skills | `web-initial-recon` 或 `elf-first-look` skill |
| 第 3 周 | 接入 MCP 与本地知识库 | 文件系统 server、知识库 server、统一工具发现 |
| 第 4 周 | 补齐 harness 与评测脚本 | 任务配置、轨迹日志、成功判定、重放脚本 |
| 第 5 周 | 建立 RAG 索引并跑小规模题集 | 题解库、工具文档库、混合检索与引用返回 |

沿着这条路线走，系统每一周都会新增一层能力，同时又始终保持可运行。它从一开始就围绕“真实任务已经能推进到哪一步”逐层扩展。


## 第 12 节：收束全文

文章一路走到这里，可以回到开头那个很朴素的问题：为什么要把大模型带进 CLI，再把它组织成 Agent 工作流。原因已经逐渐清楚了。网络攻防里的任务天然具有环境依赖、证据依赖、知识依赖和多步决策依赖。单轮聊天能够提供帮助，真正走进题目与研究现场时，系统仍然需要执行能力、观察回路、状态延续、知识补给与实验壳层。

也正因为这样，真正重要的东西始终是工程组织方式。模型提供推理与生成能力，CLI 提供真实操作表面，function calling 提供结构化调用通道，MCP 提供标准化接入层，skills 负责沉淀经验，harness 负责运行与评测，RAG 负责知识补给。它们共同组成的系统，才让 AI 与网络攻防之间出现一条可执行、可观察、可迭代、可沉淀经验的路径。

若这场分享能够留下一个清晰印象，我希望它是这样一种画面：终端里摆着题目目录、脚本、日志、容器与知识库，Agent 在受控约束下持续读取现场、调用工具、记录证据、修正路线，最后把答案与过程一起交出来。那时我们谈论的焦点已经转向“怎样把模型放进一套真正能做事的系统里”。对 AI 与网络攻防的结合来说，这条路很值得认真搭起来。

  这篇论文对第 9 节和第 10 节很有参考价值，它把 CTF 任务与 LLM 评测联系起来，适合帮助听众理解为什么题目求解天然适合做 Agent 实验。
- **Inspect Cyber**，UK AI Security Institute，2026，<https://inspect.cyber.aisi.org.uk/>
  这份文档适合支撑第 7 节、第 9 节与第 10 节，它展示了网络安全任务如何被包装成带工具、带环境、带评分的 agentic eval。
